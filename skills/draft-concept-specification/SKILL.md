## 上下文推断

不要要求用户为本次调用重新按固定格式提供输入。应从当前会话上下文推断：

1. **写作对象**：优先采用用户当前请求明确指定的概念，其次采用当前会话最近聚焦的概念；上下文明示需要处理多个概念时，将其全部作为写作对象。
2. **事实依据**：从当前会话中提取与写作对象直接相关的业务含义、属性、代表性取值、规则、约束和关系，用于编写定义、数据模型及数据模型案例。
3. **参考资料**：仅使用上下文中已经存在且路径明确的业务概念；没有可引用概念时省略该可选章节。

只使用与当前写作对象直接相关的上下文，不得混入其他主题的材料。如果多个写作对象同样可能且当前焦点不明确，先请用户确认目标概念。如果上下文不足以支撑任一必填章节，指出缺失的具体依据并停止撰写，不得补造内容。

## 核心原则

1. **聚焦业务**：使用自然语言，避免晦涩的技术概念，确保非技术利益相关者能够理解描述。
2. **最小可行内容**：定义、关键属性、数据模型、数据模型案例和规则与约束缺一不可。
3. **单一事实来源**：概念文档是术语的权威来源。用例规约和技术实现中的定义必须与概念文档保持一致。
4. **引用而非重复**：跨概念引用时，指出所引用业务概念的来源。不要在概念文档中重复属性定义，避免在多个位置维护相同信息。
5. **保持模型一致**：数据模型必须表达关键属性，数据模型案例必须使用标准 JSON，并符合模型定义和规则约束。数据模型存在变种时，每个变种使用独立的 JSON 代码块，并在代码块前最近的非空行使用加粗的业务名称注释区分。

## 工作流

1. 按照“上下文推断”确定写作对象、事实依据和参考资料。
2. 查阅**业务概念描述示例**和**业务概念描述模板**，明确相关描述维度。
3. 针对每个写作对象：
   - 严格按照**业务概念描述模板**生成业务概念描述。
   - 验证结果是否满足**业务概念描述模板**的约束。
   - 验证数据模型案例是否使用可解析且不包含注释的标准 JSON，并符合数据模型、关键属性和规则约束。
   - 数据模型存在变种时，验证每个变种是否使用独立的 JSON 代码块，并在代码块前最近的非空行使用加粗的业务名称注释。
   - 验证“规则与约束”章节是否符合**业务概念规则发现指南**。
4. 按照**审查清单**检查结果，并在输出前修正全部问题。

## 输出约定

必须根据模板生成每一份业务概念描述。未经用户授权，不得修改或优化模板结构。

## 审查清单

每份业务概念描述必须通过以下全部检查项：

- [ ] 包含“定义”“关键属性”“数据模型”“数据模型案例”和“规则与约束”五个必填章节，名称、层级和顺序与模板一致。
- [ ] “定义”说明概念的业务含义、目的和业务价值。
- [ ] “关键属性”仅描述业务特征，不包含技术实现细节。
- [ ] “数据模型”使用 TypeScript 完整表达关键属性，有限取值使用 enum。
- [ ] “数据模型案例”仅使用标准 JSON；每个代码块都能被标准 JSON 解析器解析，且不包含注释。
- [ ] 数据模型存在变种时，每个变种都使用独立的 JSON 代码块，并在代码块前最近的非空行使用加粗的业务名称注释区分。
- [ ] “数据模型案例”的字段、类型和取值符合数据模型、关键属性和规则约束。
- [ ] “规则与约束”覆盖材料中能够识别的业务规则；适用规则发现指南中的分类时，分类必须准确。
- [ ] 跨概念内容使用引用，不重复维护其他概念的属性定义。
- [ ] 写作对象和事实依据来自当前上下文，且没有混入无关主题或补造缺失信息。
- [ ] 最终文档中没有模板说明、占位符或缺乏依据的推断。
