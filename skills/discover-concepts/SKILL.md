# 识别业务概念

## 参考资料

- [航班预订用例规约案例](references/book-flight.md)
- [航班预订业务概念识别案例](references/book-flight-example.md)
- [业务概念识别输出模板](references/concept-template.md)

## 输入

用户必须提供清晰的用例规约。

### 异常处理

- 用例规约含糊时，拒绝执行，并要求用户提供更清晰的用例规约。不得推断缺失细节。

## 核心原则

1. **聚焦业务**：识别具有独立业务含义、价值或边界的概念，不提取纯技术实现元素。
2. **依据可追溯**：每个概念必须能够追溯到用例规约中的描述。
3. **边界明确**：合并同义表达，区分容易混淆但业务含义不同的概念。
4. **关系精确**：仅报告有材料依据的业务关系；不得为完善模型而补造概念或关系。

## 工作流

### 1. 识别候选业务概念

阅读用例规约，识别出名词术语，并进行简要描述（例如：**订单：承载航班、乘客与支付状态的购票业务对象**）

重点关注以下位置：

- 参与者与系统交互的协议：预订、支付
- 流程中被创建的对象：订单、机票、退款
- 流程中被记录的数据：乘客信息、价格明细、座位库存
- 流程中被查询或校验的信息：航班、票价等级、乘客身份
- 流程中需要持久化的结果：订单、支付结果、机票、出票通知

### 2. 筛选候选业务概念

针对候选的名词术语，按照如下标准进行初步筛选：

- 名词术语是否只是其它名词术语的属性
- 名词术语是否具有独立生命周期
- 名词术语是否作为流程节点间的业务凭证
- 名词术语是否作为 **系统** 与 **参与者** 之间的交互协议
- 名词术语是否需要跨用例共享

针对筛选后的概念，合并相同业务语义的概念，处理同词异义和异词同义问题。

### 3. 用例规约回溯

代入用例规约中的行为描述，判断每个动作关注的业务概念。例如：

- _选择航班_ → _航班_
- _临时保留座位_ → _座位保留_ + _订单_
- _提交支付_ → _支付_ + _订单_
- _完成出票_ → _机票_ + _订单_
- _发起退款_ → _退款_ + _支付_

**如果特定行为描述无法匹配明确归属业务概念，则推断出现业务概念遗漏，需要进行补充。**

### 4. 建立关联关系

遵循 `UML` 定义的 `泛化 + 组合 + 聚合 + 关联 + 依赖` 建立业务概念间的关系，例如：

- _订单_ 关联 _航班_
- _退款_ 依赖 _支付_

### 5. 收敛与输出

对照理解 **航班预订用例规约案例** 与 **航班预订业务概念识别案例**，重新校准业务概念取舍、关系表达。

严格按照 **业务概念识别输出模板** 组织内容。模板中的引用块、HTML 注释、格式指导、示例和占位符只用于起草，不得出现在最终输出中。

## 审查清单

- [ ] 所有概念都来自用例规约，并附有可追溯的识别依据。
- [ ] 概念具有独立业务语义，不是页面、数据库表、接口或其他纯技术元素。
- [ ] 概念具有独立生命周期，不是属性、状态或其它无生命周期的元素。
- [ ] 同义表达已合并，易混淆概念的边界已说明。
- [ ] 概念关系有材料依据，并使用定义明确的 UML 关系。
- [ ] 最终输出不包含模板说明、注释、格式指导、示例或占位符。
- [ ] 输出不包含完整业务概念规约，也没有缺乏依据的推断。
