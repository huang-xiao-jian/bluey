# 识别业务概念

## 输入

用户必须提供清晰的用例规约。

### 异常处理

- 用户未提供用例规约时，拒绝执行，并要求提供用例规约。技术设计文档、通用业务需求和其他业务文档均不能替代用例规约。
- 用例规约含糊时，拒绝执行，并要求用户提供更清晰的用例规约。不得推断缺失细节。

## 识别原则

1. **聚焦业务**：识别具有独立业务含义、价值或边界的概念，不提取纯技术实现元素。
2. **依据可追溯**：每个概念必须能够追溯到用例规约中的参与者、业务对象、规则或交互。
3. **边界明确**：合并同义表达，区分容易混淆但业务含义不同的概念。
4. **关系精确**：仅报告有材料依据的业务关系；不得为完善模型而补造概念或关系。

## 工作流

<!-- 以下提取策略是启发式建议，无需机械遵循。 -->

1. 阅读用例规约，识别反复出现的名词术语、核心参与对象、受业务规则治理的实体，以及具有独立业务价值或边界的对象。
2. 合并指向同一业务含义的候选项，并说明可能造成歧义的名称。
3. 为每个概念归纳其业务含义、识别依据和边界。
4. 分析概念间有材料依据的业务关系。
5. 按照审查清单检查结果，并在输出前修正全部问题。

## 输出约定

输出一份“业务概念识别结果”，包含：

1. **概念清单**：每个概念的名称、一句话业务含义、识别依据和业务边界。
2. **概念关系**：使用定义明确的 UML 关系描述相关概念，并注明依据；没有充分依据时明确写出“未识别到有依据的关系”。
3. **待澄清项**：列出会影响概念取舍或边界判断、但用例规约未明确的信息；没有待澄清项时省略。

不要撰写“定义”“关键属性”“规则与约束”和“关系”组成的完整业务概念规约。完整规约由 `$draft-concept-specification` 负责。

## 审查清单

- [ ] 所有概念都来自用例规约，并附有可追溯的识别依据。
- [ ] 概念具有独立业务含义，不是页面、数据库表、接口或其他纯技术元素。
- [ ] 同义表达已合并，易混淆概念的边界已说明。
- [ ] 概念关系有材料依据，并使用定义明确的 UML 关系。
- [ ] 输出不包含完整业务概念规约，也没有缺乏依据的推断。
