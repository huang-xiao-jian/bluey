# 起草用例规约

## 输入

用户至少需要清楚说明以下信息：

1. **参与者（Actor）**
2. **业务目标**

用户可以直接描述这些信息，也可以提供用例分析、用户故事、工作流定义或类似材料。

## 工作流

### 1. 理解需求

提取用户明确提供的参与者、业务目标和其他业务事实。参与者或业务目标缺失、不明确时，要求用户补充；两者明确后即可开始大纲设计。

### 2. 设计大纲

根据已有信息推断用例内容，形成包含以下项目的简洁大纲：

1. **用例名称**
2. **参与者**
3. **业务目标**
4. **可验证的前置条件**
5. **基本事件流、备选事件流和异常事件流**
6. **成功与失败时的系统状态**
7. **业务规则和约束**
8. **用例直接相关的特殊需求**

将不由用户原始描述直接支持的推断集中列为**关键假设**。没有合理依据的特殊需求写“无”；存在合理扩展依据时，可以在大纲中提出扩展点。

只返回大纲、关键假设和待澄清问题，然后停止，不得继续起草完整用例规约。

### 3. 业务澄清（阻塞）

要求用户审阅大纲、修正关键假设并回答待澄清问题。根据用户反馈更新大纲、关键假设和待澄清问题，必要时重复本步骤。

本步骤始终阻塞后续流程。用户回答问题、补充信息或确认局部内容时，继续停留在本步骤。只有用户明确表示“进入下一步”“开始细化”或给出同等明确的继续指令后，才能解除阻塞。

### 4. 阅读关键参考资料

阅读并分参考资料，以明确业务用例规约的撰写要求

- [使用 Mermaid 补充说明复杂业务流程](adr/mermaid.md)
- [用例规约模板](references/template.md)
- [用例规约示例](references/example.md)

### 5. 起草用例规约

按照模板结构和用例分析最佳实践，将业务澄清后的大纲细化为完整用例规约，并遵循 ADR 的流程表达决策。

模板中的说明、格式指导、示例和占位符只用于起草，不得出现在最终产物中。

未经用户授权，不得擅自更改或优化模板结构。

### 6. 按清单审查

返回结果前逐项检查，并修正所有不符合项：

- [ ] 用户已经参与业务澄清，并明确指示进入下一步。
- [ ] 完整用例规约与业务澄清后的大纲一致，不包含未经澄清的新业务假设。
- [ ] 产物包含参与者、简要说明、前置条件、事件流、后置条件、业务规则和特殊需求全部必填章节。
- [ ] 前置条件可验证。
- [ ] 事件流使用文本分别完整描述基本事件流、备选事件流和异常事件流。
- [ ] 每个事件都是可观察的参与者行为或系统响应。
- [ ] 业务规则不引用事件序号或 Mermaid 节点名。
- [ ] 仅当流程包含较多相互影响的分支、循环、回退、恢复路径或跨事件流转换时，才使用 Mermaid 图作为补充说明。
- [ ] Mermaid 图存在时，只呈现事件流中已有的业务语义，并与事件流一致。
- [ ] 后置条件分别清楚说明成功与失败时的系统状态。
- [ ] 特殊需求仅包含与当前用例直接相关的非功能需求；没有已知内容时明确写“无”。
- [ ] 可选的扩展点仅在业务澄清后的大纲提供充分依据时出现。
- [ ] 全文术语一致。
- [ ] 最终产物不包含模板说明、格式指导、示例或占位符。
